# Rubric review: architect REPLAN amendments of 2026-11-20

Reviewed: `architecture-agentic-manager.md` (working tree, uncommitted), passages marked "amended 2026-11-20, architect REPLAN", AD-48, the three new Consistency Conventions rows, the changed Stack rows and the two new Deferred rows, against the last eight `.memlog.md` entries, the epic 1 Notes "Architect REPLAN scheduled" list, `Cargo.toml`, `deny.toml`, `docs/crate-notes/*`, `crates/am-store/src/project.rs`, `crates/am-config/src/snapshot.rs` and `crates/am-config/src/kinds.rs`. Read-only review; nothing else was edited.

## Verdict

The amendments cover all six queued REPLAN items, and the four Stack ratifications match the code exactly. AD-48 and the AD-32 runtime-folder move are not yet safe to build from. AD-48's "effective allow-list" mixes Account pins into the list that tools use, and HostPattern cannot express those pins. The runtime-folder move leaves the bootstrap order, the resolver's owner, test injection, the legacy-move locking and the AD-16 baseline of a fresh runtime folder undefined. Each of these would let two stories diverge. Fix the high findings before Sofia restates the tickets. The medium and low findings can be fixed in the same edit.

## Findings

### High

**H1. AD-48 Rule and AD-12: the "effective allow-list" merges Account pins into the list used by tool, link and Source fetches. HostPattern cannot represent those pins, and MCP-over-HTTP hosts have no place in it.**
- AD-48 defines effective allow-list = `allowed_hosts` + "the pinned host of each Account the seat uses". It then says every "seat's allow-list" in AD-12, AD-30, AD-39 and AD-46 means that list. Account pins can be loopback `127.0.0.1:<port>`: an owner-added OpenAI-compatible Account, a self-hosted crawl service on `localhost:3002`, or LM Studio on `:1234` (AD-12). So the link-list, `read_url`/`read_website` and Source-scope checks now pass for the model server's or crawl service's loopback host. AD-12's loopback resolver exception is worded per Account ("a local Account … on 127.0.0.1"), not per request. Nothing says a request without that Account cannot use it. This widens what tools can reach, and the AD-48 migration claims to be "not widening".
- AD-48 also says HostPattern refuses IP literals, `localhost` and ports, and that "nothing else matches hosts". Account pins (`127.0.0.1:<port>`, a port on an https host) cannot be HostPatterns, so either the rule is broken on day one or the pins are matched by something else.
- Ports are undefined. Does pattern `example.com` admit `example.com:8443`? The validator and `am-net` can answer differently, which is the divergence AD-48 says it prevents.
- MCP-over-HTTP servers (AD-26) are neither `allowed_hosts` nor Accounts, so their hosts are in no allow-list. Spike criterion 5's live server is at `http://127.0.0.1:3001/mcp`. Under AD-48 plus AD-12 it is unreachable: HostPattern refuses loopback and the resolver blocks it. am-mcp and am-net will each improvise an answer.
- Fix: keep two separate sets. (a) The seat's HostPatterns gate tool, link, Source and MCP fetches. (b) Each Account's exact pinned origin (scheme, host, port) is honoured only for requests that carry that Account. Use an `AccountOrigin` type, not HostPattern. Say whether a pattern admits any port or only 443/80. Give MCP-HTTP servers an exact pinned origin in their `tools.yaml` record, approved with the server (AD-26), including the loopback case under the same rules as owner-added loopback Accounts.

**H2. AD-32 Rule, Binds and AD-47: the runtime folder's bootstrap, owner and test injection are unspecified, which contradicts AD-16, AD-24, AD-47 and the current code.**
- Order problem. `project_id` is written "when the app creates or first opens the project (a `ConfigEdit` by `Actor::System`)". A ConfigEdit carries a History entry and an audit entry (AD-16, AD-25), and both live in `state.db`. `state.db` lives in the runtime folder, which is named by the id being written. The spine must give the order: mint the id, write `company.yaml` atomically through am-config, open or create the store, then record the History and audit entries for that edit.
- Owner problem. Only am-config may read `company.yaml` (AD-16), and today `am_store::open_project(root)` (`crates/am-store/src/project.rs`) derives `root/.agentic` itself and writes a `.gitignore` into it. After the move, something must resolve `project_id` → runtime path → canonical-root record, and AD-32's Binds name only `am-app`, `am-desktop` and the release pipeline. Name the resolver: am-app, using am-config for the id. State the new store entry point (`open_project(runtime_dir, project_root)`), and bind am-store and am-config in AD-32.
- Portability and tests. `~/Library/Application Support` is a macOS path. Under AD-47 it must sit in an adapter whose non-macOS branch returns "not supported". am-store's unit tests, though, run on the Linux CI job. Today they open tempdir projects; under this design they would need the real home folder or the error branch. The spine should say the runtime base directory is injected: resolved by an am-app macOS adapter, passed as a parameter, and a tempdir in am-testkit and tests. Tests must never write into the real `~/Library`.
- Templates and fixtures. `templates/roles/*/company.yaml` and `fixtures/projects/*/company.yaml` exist, and `just check` runs `agentic validate` over them. The spine must say three things. Shipped templates and fixtures carry no `project_id`. Creating a project from a template mints a fresh one. `agentic validate` accepts a missing `project_id` and never writes it. Otherwise every Company A instance shares one id and is refused as a copy, or validate rewrites tracked repo files.

**H3. AD-32 Rule, the legacy move and copy/move detection: data-loss and trust gaps.**
- The legacy move copies, verifies and removes `<project>/.agentic/`, but nothing says it first takes that folder's `lock`. Story 1.6's code holds the lock through a live writer, so an older binary still serving the project can commit after the sha256 check and before removal. Those commits are lost. Require the legacy lock, and the new runtime lock, for the whole move.
- The move has no idempotence rule. If removal fails, or the owner later restores an old copy of the project that still holds `.agentic/`, the next open finds both a legacy folder and a runtime folder. The rule as written copies again and overwrites newer state. Specify that when both exist the open is refused in words, or the runtime folder wins, and the legacy folder is never copied over it.
- A legacy folder inside OneDrive or iCloud may hold dataless files (evicted backups or knowledge files). Copying them forces a download, and offline the project cannot be opened at all. Say whether that is accepted or whether the copy runs under the AD-30 download wait.
- AD-16's approved grant-set fingerprint lives in `state.db`. A fresh runtime folder has no fingerprint. That happens when a copy is given its own id, when a project is opened on another Mac, or when the runtime folder was deleted. The spine leaves the baseline undefined. "Adopt the current grants" silently accepts any outside edit made meanwhile. "Empty baseline" means a two-step confirmation of every grant on first open. Pick one; the second is safer. This is now a routine path, because copying a project folder no longer carries its state.
- "A recorded root that no longer exists is a move." An unmounted external volume or a signed-out CloudStorage provider also looks like a missing root. Opening a clone during that window re-points the state, and the original becomes "the copy" when it returns. At least state this, and require canonical, case-insensitive path comparison (APFS default, firmlinks) for "another root".

### Medium

**M1. Operational envelope of the runtime-folder move (AD-32, Structural Seed, Deferred) is incomplete.**
- Backups and restore. Daily and pre-migration backups now sit only in `~/Library/Application Support`. The owner's cloud-synced project folder no longer carries any state, which was the owner's intent. But the spine never says how a backup is restored into a runtime folder on another Mac (id, recorded root, `backup-key:<project-id>` from the recovery key). The AD-38 phrase "does not travel with the project" now applies to the whole runtime history: ledger, audit, approvals, knowledge, records.
- Orphans. Nothing removes a runtime folder whose project was deleted or re-identified. Knowledge files, records and workspaces accumulate in a hidden location. Add a "Forget this project" path or a Doctor listing, or record the gap as Deferred.
- Owner-facing folders. Drop folders (`.agentic/drop/<source-id>/`) and reference files (`.agentic/knowledge/<seat-id>/`) are places the owner puts files. `mockups/key-seat-sheet.html` shows `.agentic/drop/d1-e2` as if it were in the project, and they now live under `~/Library/Application Support/…`. The UX spine needs an affordance ("Add files…", "Reveal in Finder") and a REPLAN item to Sally through Sofia.
- Deferred row "Product name in binary, bundle id and keychain service". A rename now also orphans every runtime folder under `agentic-manager-projects/`. Add the runtime root to that row's migration, or two stories will rename different things.

**M2. AD-30 (cloud-only files) contradicts unamended AD-40 and amended AD-47.**
- AD-40 tracks `files: new_or_changed` with a folder cursor of "path and sha256". Hashing a cloud-only file downloads it, while AD-30 says "A fan-out over a folder … lists without downloading". Say whether the cursor uses size, mtime and provider metadata for files with `local: false` and hashes only on read, or that `new_or_changed` downloads.
- AD-30 says FileResidency "elsewhere every file reads as local". AD-47, amended in the same pass to list FileResidency, says every non-macOS adapter branch returns "not supported on this platform yet". Pick one. "Reads as local" is the useful one for Linux CI, so add it to AD-47 as the stated exception.
- The "download wait" is a new per-seat and per-step field whose increase is widening. AD-15's enumerated widening list ("raising any cap (seat, workflow, …)") does not name it, and `is_widening` is built from that list. Add it there.

**M3. AD-30's "What leaves this Mac" disclosure covers only the two cloud-storage roots.** AD-32 itself says iCloud Desktop & Documents syncs `~/Documents`, which is why path-based sync detection was rejected. A `read_write` folder in `~/Documents` or `~/Desktop` therefore syncs files written by seats with no disclosure, so the disclosure is keyed on the same unreliable path test the amendment rejects. Base it on FileResidency or File Provider membership of the root (the adapter already exists), or disclose for every `read_write` folder. Separately, a cloud-only read makes the provider download outside `am-net`. State it as declared, not enforced, as AD-26 does for stdio MCP.

**M4. AD-48 HostPattern has no pattern-against-pattern relation, the egress_hosts migration can fail, and Source scope hosts are left open.**
- Three checks need to know whether one pattern covers another, not just whether a host matches: "replacing one with a broader one" (widening); AD-12 and AD-39's "Source scope hosts must be on the seat's allow-list"; and `is_widening`'s set difference. Note that `example.com` replaced by `*.example.com` adds hosts without being "broader" (the wildcard excludes the apex). Define `HostPattern::covers(&HostPattern)` and state the widening rule as "any added pattern not covered by an existing one".
- Source `scope.allowed_hosts` (AD-39, in `kinds.rs`) has the same field name as the seat's list, but AD-48 does not say whether it accepts `*.` patterns. "Nothing else matches hosts" implies it does, while today's code accepts exact hosts only.
- The current `egress_hosts` validator (`kinds.rs` ~l.541) accepts mixed case and IPv4-looking values such as `1.2.3.4`. HostPattern refuses both. The "keeps effective hosts" migration must lowercase, and must say what happens to an entry that is not a valid pattern. Also say what each seat may reach while the config-migration diff is shown but not yet accepted.

**M5. The Globs convention misses two pattern sites and conflicts with the Firecrawl adapter.**
- The `list_files` glob argument (supplied by the model) and AD-40's `over_folder` route `match` globs are linked-folder globs, but the convention names only `include`/`exclude`. Say they are also case-insensitive and go through the helper, or the router and the validator will disagree on `*.PDF`.
- Firecrawl v2 `includePaths`/`excludePaths` are regex, not glob, patterns (worth re-checking on docs.firecrawl.dev). "globset only" plus AD-39's "from the globs" leaves the translation unspecified. State that the adapter sends the helper's `Glob::regex()` output and re-checks every returned URL against the helper before storing it.

### Low

- **L1. Structural Seed (~l.589–590).** The tree puts a `.agentic/` child under `~/Library/Application Support/agentic-manager-projects/<project-id>/`. Read literally, that gives `<id>/.agentic/state.db`, while the Runtime paths convention means `<id>/state.db`. List the contents directly under `<project-id>/`.
- **L2. Stale wording in unamended passages.** AD-35 (l.344) still says "the git-ignored `.agentic/knowledge/`". AD-48's list of ADs whose "seat's allow-list" means the effective list omits AD-11 (the tainted-read rule (a)), AD-38 (link-host validate warning) and AD-41 (receiving seats' allow-lists). The validator's fix text in `kinds.rs` still says "add it to egress_hosts in tools.yaml" (a story fix, but the spine should not leave the list partial).
- **L3. Stack.** The "Supporting crates" row omits `base64` (`=0.23.1` in `Cargo.toml`). Saying the manifest "owns their versions" weakens AGENTS.md's "versions are pinned exactly in the architecture § Stack". Keep it an exhaustive list, or move every pin into the table. The rmcp and process-wrap rows omit `default-features = false`, which `Cargo.toml` sets; rmcp's defaults would bring back `server`.
- **L4. AD-7 retention.** "Three newest pre-migration backups" is new. Per `docs/crate-notes/rusqlite.md` these are plaintext `VACUUM INTO` copies (`backups/state-v<from>-<ts>.db`), while AD-32 encrypts the daily backups. Say whether pre-migration copies are encrypted too, and that pruning matches only pre-migration names, never the 14 daily ones.
- **L5. AD-15 "Every committed widening is audited".** It says "the apply". Name the AD-16 Reload and startup confirmation, imports and the AD-48 migration as well, so no path skips the per-widening entries.
- **L6. UX spine.** `EXPERIENCE.md` still says "~/Library … refused in words" on Link folder. It needs the cloud-root exception, through Sofia. That is not an architecture edit, but the level below will diverge until it is done.
