# Reality-check review: spine update 2026-11-22 (owner answers 2)

Scope: the changed text only (`git diff --word-diff` of `architecture-agentic-manager.md`, working tree on top of 3cdaeff): AD-13 (pseudo-terminal condition, app data dir from `$HOME`), AD-15 *References*, *Change*, *Terminal*, AD-17 *Recovery*, AD-38, the Deferred rows (sandboxed code execution, skill scripts, `migrate --as`) and Open Questions. Lens: is every committed claim true of the code in `crates/` and of story 2.12's plan, or only asserted? No new technology is named, so no version check was needed.

Verdict: **pass with fixes.** Most claims hold against the code. Two claims describe a store behaviour that does not exist and is not owned by any story (the `recovered` mark) or is unsafe as worded (moving a WAL store aside as one file). Three more overstate or misstate what the code does.

## High

### H1. The `recovered` mark is stated as existing behaviour, but nothing writes it and no story builds it
- Changed text (AD-17 *Recovery*): "when the user store is missing (am-app then creates one marked `recovered`)". AD-17 *Migrate* (from the earlier gate) also relies on a store "not marked `recovered`".
- Evidence: `grep -rni recover crates --include=*.rs` returns nothing. The user store is created by `UserStore::locked` and the migration runner, which stamp only `application_id` and `user_version` (`crates/am-store/src/user.rs:174-190`, `crates/am-store/src/migrations.rs:213-227`). `UserReader::open` reads a missing `user.db` as empty and does not create one (`crates/am-store/src/user.rs:365-369`). In the tickets, story 2.13 only *reads* the mark (epic-accounts-model-routing `tickets.toml` line 56, "is not marked `recovered`") and story 9.19 assumes it exists ("am-app has created a new one marked `recovered`"). No story is given the work of writing it. Story 2.12 is already built and creates unmarked stores.
- Consequence: if a Mac lost `user.db` after 2.12 shipped, `add` recreates it with no mark. Story 2.13's carry-over guard (C1, "no user-store record for the id and a non-recovered store") then fails open: an old project confirmation is carried into a store the owner never confirmed against.
- Suggested wording (AD-17 *Recovery* and *Migrate*): "From epic 2 story 13, the first story that reads the mark, am-app marks a user store it creates while the user Accounts file or `backups/accounts-migrate/` already exists as `recovered`. A store created before that story counts as `recovered` when the first History entry of the user Accounts file has a non-empty before-hash (the file was there before the store)." Sofia then adds the mark and that rule to 2.13's description and verify.

### H2. Moving a WAL store aside "byte for byte" as one file loses data and can corrupt the new store
- Changed text: "a store that is unreadable or not a user store is only moved aside, byte for byte, to an `AppDataLayout` path … so am-app can create a store marked `recovered`".
- Evidence: the user store runs in WAL mode (`crates/am-store/src/user.rs:8`). am-app already treats `user.db-wal` and `user.db-shm` as part of it (`crates/am-app/src/user.rs:54-62`). If only `user.db` moves, the copy set aside is missing any commits not yet checkpointed. The old `-wal` left at the original path can then be replayed by SQLite into the newly created `user.db`, so the fresh `recovered` store would start with foreign pages.
- Suggested wording: "moved aside, byte for byte and sha256-checked, together with its `-wal` and `-shm` files, to an `AppDataLayout` path; am-app creates no new store while any of the three is still at the old path." Apply the same wording to story 9.19's description and verify (case (b)/(c): assert the three files moved and none left behind).

## Medium

### M1. The Deferred row for `migrate --as` binds story 2.13 to `am_config::is_widening`, which does not exist until epic 4 story 17
- Changed text (Deferred): "The plan decides it inside `am_config::is_widening` and AD-15, never by a second path". The restated 2.13 verify adds "classified by `is_widening` as the plan decides (a failing-first test asserts that classification)".
- Evidence: there is no `is_widening` in `crates/`; the only mention is a comment in `crates/am-config/src/session.rs:25` ("the privilege-widening check of a Reload (epic 4)"). The function is built by epic 4 story 17, "One privilege-widening classifier for every config path" (epic-triggers-budgets-safety-floor `tickets.toml` line 143, `after = [10, 15, "1.12", "1.13", "1.14"]`), which builds after epic 2. The same story already says epic 2 story 1's interim CLI path "goes through this classifier once it ships". So 2.13 cannot write a test against `is_widening` without building it early, which would also span milestones.
- Suggested wording: "2.13's plan decides the rule and records it here. Epic 4 story 17 encodes it as `is_widening`'s `ConfigMigration` arm, with its failing-first test. Until then `migrate --as` applies the rule as the interim CLI Account edit does (AD-15), and never through a second classifier." Sofia should restate 2.13's verify to match and add the case to 4.17's table-driven test.

### M2. "Every `agentic accounts` command is refused while any reachable project enables" a stdio MCP server overstates AD-15 *Open* and the code
- Changed text (AD-13 condition): "every `agentic accounts` command is refused while any reachable project enables one (AD-15 *Open*)".
- Evidence: AD-15 *Open* says that `add`, `change` and `remove` "are refused while any reachable project … enables a stdio MCP server or a Source with `render: true`". The code calls `no_owner_child` only from `add` (`crates/am-app/src/accounts.rs:640`), `remove` (`:955`) and the shared re-read under the lock (`:595`). `list` (`:1100`) and `test` (`:1239`) do not, and the module doc says both "run with any stdin" (`:55-56`).
- Suggested wording: "every `agentic accounts` command that adds, changes, removes or confirms an Account (`add`, `change`, `remove`, `migrate`) is refused while any reachable project enables one (AD-15 *Open*); `list` and `test` confirm nothing."

### M3. "while the keychain stays the owner's" is contradicted by the project's own tests
- Changed text (AD-13): a process that starts `agentic` with another `HOME` "points it at an app data dir that process wrote …, while the keychain stays the owner's".
- Evidence: `crates/am-app/tests/accounts_tty.rs:12-16` and `:191-195` say: "With HOME in a temporary folder macOS finds no default keychain". The test has to create a keychain, make it the default and unlock it under that `HOME`. So on macOS the keychain search list also follows `HOME`. The residual is still real, because the same-user process can point that list back at the owner's login keychain, but the mechanism stated in the spine is wrong.
- Suggested wording: "… with its own Accounts file and user store. The keychain search list follows `HOME` as well, but that process can point it at the owner's login keychain, so the owner's keys stay reachable. This residual is recorded …"

## Low

- **L1. Ambiguous "user database".** AD-13 says "no lookup of the home folder from the user database". Elsewhere the spine and the owner's own quote in *Recovery* ("lost user database") use "user database" for the user store. Fix: "no lookup of the home folder from the passwd entry (`getpwuid`)".
- **L2. "still no env var, flag or setting that names another app data dir" is not literally true.** `XDG_DATA_HOME` does exactly that off macOS (`crates/am-app/src/runtime.rs:131-134`), and `HOME` does it everywhere. Fix: "and no env var, flag or setting beyond `HOME` (and `XDG_DATA_HOME` off macOS) that names another app data dir".
- **L3. "not a user store (another `application_id`)" is narrower than the code.** The code also refuses a non-empty database with `application_id` 0 ("not a database this app made") and a negative `user_version` (`NotOurs`) (`crates/am-store/src/user.rs:62-90`). Story 2.12's plan "Wrong file" rule (plan line 89) names only "another non-zero `application_id`". Fix: "not a user store (another `application_id`, or a non-empty database with none)". Bring the plan wording into line.
- **L4. "an `AppDataLayout` path" names no path that exists.** `AppDataLayout` has `accounts_file`, `user_db`, `user_lock`, `backups_pre_migration`, `mac_id` and `serving_dir` only (`crates/am-domain/src/runtime.rs:45-88`). Fix: name the new path, for example `AppDataLayout::set_aside()` → `<app data dir>/set-aside/user-<UTC timestamp>.db` (plus `-wal` and `-shm`), added by epic 9 story 19. Also say "unreadable" excludes loose permissions or ownership, which am-app already refuses with a `chmod` fix (`crates/am-app/src/user.rs:40-75`). Doctor reports those and never moves the file.
- **L5. "the app's children are started by the app from config, never from a tool call's arguments" is loose.** The extractor and `__render` children are started *in response to* reads and Source loads, with a program and arguments the app fixes. Stdio MCP comes from `StdioSpec` config with `env_clear` (`crates/am-mcp/src/lib.rs:50-58`). Fix: "no tool call, skill, Source or model output names a program, its arguments or its environment; the app's children are fixed programs or the owner's configured stdio servers".
- **L6. Story 2.12's plan is now out of date.** Its `deferred[0]` (`$HOME`, "owner call whether to tighten") is decided by this update but not marked. Sofia should annotate it "decided 2026-11-22: kept, recorded residual (AD-13)" so the plan does not read as open. Frontmatter only; not a spine change.

## Verified (no finding)

- App data dir and runtime base come from `HOME`, with `XDG_DATA_HOME` only off macOS: `crates/am-app/src/runtime.rs:118-134`. No other env var selects them; the other `HOME` reads are `crates/am-config/src/lib.rs:259` (`~` expansion) and `crates/am-tools/src/lib.rs:73` (link refusal).
- The Terminal predicate is stdin and stdout `is_terminal()` (`crates/am-app/src/terminal.rs:27-29`), so a pseudo-terminal passes, as AD-13 and AD-15 *Terminal* state.
- There is no shell or process tool. The am-tools API is folder access only (`crates/am-tools/src/lib.rs`). The only spawn sites are am-mcp's stdio child from config, `identity.rs`'s fixed system tools, `/bin/ps` in `runtime.rs:544` and `open <url>` in `main.rs:292`.
- The skill loader refuses a `scripts/` folder and any executable bit (`crates/am-config/src/skills.rs:22-36`, `:90-93`), which matches AD-38 "no file in a skill folder is ever run".
- The Key-use check runs before any keychain read: `test` calls `checked()` before `secrets.get` (`crates/am-app/src/accounts.rs:1239-1270`). With a lost store, check 3 (no History after-hash) refuses every Account, which matches *Recovery*'s "refuses every key use … before any keychain read".
- A newer store is refused, naming the newer app (`UserTooNew`, `crates/am-store/src/user.rs:91-97`), which matches "a newer store is never moved, and Doctor names the newer binary".
- `remove` refuses on unreachable projects unless `--force` is given, and `add` only names them (`crates/am-app/src/accounts.rs:549-556`, `:966-992`), which matches *References* "*Remove* refuses on them; *Change* does not".
- The Open Questions row on blocking in `NetEgress::send`, with a lock wait of up to 10 s, matches `LOCK_WAIT = 10 s` (`crates/am-app/src/user.rs:32`), the `key_use::check` call in `crates/am-app/src/egress.rs:122`, and 2.12's plan `deferred[2]`.
- The About page story (9.11, restated) lists all three residuals, `HOME` included. Epic 11 story 9's CI check that a residual is missing from the page covers the `docs/` threat model.
