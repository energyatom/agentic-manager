# Adversarial review — skill import from GitHub (AD-12, AD-15, AD-38 amendment, 2026-11-22)

Reviewer lens: adversary. Scope: the uncommitted spine diff on `replan/2026-11-22-skill-github` (AD-12 "App requests" and "No telemetry", AD-15 CLI-class list, AD-38 "Importing" and "From GitHub", two Deferred rows, three seed/map lines), read against AD-6, AD-10, AD-11, AD-13, AD-15, AD-16, AD-25, AD-27, AD-30, AD-32, AD-38, AD-48, the AGENTS.md Policy section, the built code (`crates/am-net/src/lib.rs`, `crates/am-domain/src/net.rs`, `crates/am-config/src/skills.rs`, `kinds.rs` `fn skill`, `fields.rs`) and the neighbouring tickets (2.2, 4.6, 4.10, 4.11, 4.16, 5.11, 9.16). The owner's decision is taken as final; every finding is about how the spine rules it.

**Verdict: pass-with-fixes.** The frame is sound (pinned commit, fixed two-host set outside config and outside every seat list, no credential, expansion in the sandboxed child, nothing trusted before the owner's apply). 4 high, 9 medium and 6 low findings follow; no critical. The four high ones each need one or two sentences in the spine before story 9.16 (and, for H3, before story 2.2, which is next in build order) is built.

Facts checked on the live public API on 2026-11-22 (unauthenticated, generic user agent, 7 requests, `Accept: application/vnd.github.sha`):

## High

### H1 — The app vouches for a repository that never held the commit (fork commits, pull-request refs, short ids, revision expressions)

- **Spine text (AD-38, Pin and Source record):** "The app resolves the ref to one full commit SHA through AD-12's app requests (… the answer must be 40 hex characters) and downloads the zip archive of exactly that SHA" and "It sets both from what the app itself resolved … the Proposal's confirm step shows the URL, the commit and the two hosts".
- **Scenario.** GitHub answers `commits/<ref>` for any commit in the repository's fork network and for `pull/<n>/head` (checked above). An attacker forks a well-known skills repository, commits a poisoned skill to the fork (or just opens a pull request), and passes round `https://github.com/<trusted-owner>/<trusted-repo>/tree/<sha>/skills/x` or `…/tree/pull/123/head/skills/x`. Both match the accepted URL form. The lookup answers 200 with 40 hex, the archive downloads, and the confirm step, the History entry, the audit entry and `agentic-source-url` all say the skill came from the trusted repository. The trusted owner never accepted that commit. The owner still sees the full diff, but the one line they lean on ("from <trusted-owner>/<trusted-repo>") is false, and it is the app saying it, not the file. A 7-hex or `main~1` ref also resolves, so "ref" is wider than a branch or tag in ways the URL rule does not say.
- **Closing sentence (AD-38, Pin):** "`<ref>` must be a branch or a tag of that repository: every lookup asks for `heads/<candidate>` and then `tags/<candidate>`, never the bare candidate (`HEAD` alone is asked bare); a candidate must pass git's ref-name rules, so a commit id, a pull-request ref (`pull/…`, `refs/…`) or a revision expression (`~`, `^`, `@{`) is refused in words: 'Give a branch or tag; a commit link cannot be checked against this repository.'"
- **If the owner wants commit permalinks kept** (press `y` on GitHub gives `/tree/<sha>/…`): accept only a full 40-hex id, and add "the confirm step and the source record then say 'commit given by id; GitHub does not say it is on a branch of <owner>/<repo>'". This is a question for the owner; refusing is the smaller rule.
- **Side effect to settle with M4:** two lookups per candidate changes the request budget.

### H2 — Nothing says the bytes applied are the bytes reviewed; "when the import ends" is undefined

- **Spine text (AD-38, Before apply):** "the archive and its expanded files are held in memory or in an owner-only temporary folder in the runtime folder (a `RuntimeLayout` path) and are removed when the import ends and at the next start."
- **Missing rule:** where apply takes its bytes from, and when the import "ends" (at Proposal creation, or at apply or dismiss).
- **Two builders, both to the letter.** Builder A ends the import at apply: the Proposal holds paths into the temporary folder and apply copies from it. Builder B ends it at Proposal creation and puts the text in the Proposal's patches. With A, (1) a restart removes the folder and every pending import Proposal is dead; (2) a same-user process (a stdio MCP server or the rendering browser, both owner-uid by AD-13, both allowed while the UI class imports) rewrites `SKILL.md` in the runtime folder after the diff was drawn, and the apply writes unreviewed text into `skills/<id>/` as `Instruction`. AD-15's "Apply refuses if any file it touches has changed since" covers project files only, not the staged source. That is taint laundering through the staging folder.
- **Closing sentence (AD-38, Before apply):** "Each import Proposal holds the full text of every file it will write (SKILL.md exactly as it will be written, the two source keys included) with its sha256; apply writes those bytes and never reads the temporary folder, the archive or the network again. The import ends when the chosen skills' Proposals are created or the list is closed, and the temporary folder is removed then."
- Also covers the folder and zip paths, which have the same gap for a zip the owner still holds on disk.

### H3 — The fixed set can land in the egress client's policy-wide list, and "an app purpose in their place" has no shape that keeps it exclusive

- **Spine text (AD-12):** "Each request carries its seat and Account (or, for the one app request kind below, an app purpose in their place)"; "It is never written to, merged into or matched against any seat's `allowed_hosts`"; "no tool manifest, ToolGate path or engine run can build a request with an app purpose, and a test proves it."
- **Built code today.** `am_domain::Caller { seat: Option<String>, account: Option<String> }` derives `Default`, and `HttpRequest::get` and `post_json` build a caller with neither. `am_net::EgressPolicy { allowed_hosts: Vec<String> }` is one list for the whole client. Story 2.2 (next to build) completes the client; story 9.16 (much later) adds the import.
- **Two builders.** The 2.2 builder adds `purpose: Option<AppPurpose>` beside the two options and, to make the import pass, has `SkillImport` add the two hosts to the policy's list. No seat's `allowed_hosts` was touched, so the quoted sentence holds, yet every request the client checks against that list (an Account call on a redirect, an MCP-over-HTTP call, the local-service proxy of AD-45, a `Fetcher` request that reaches the client after ToolGate) now passes for `api.github.com`. Separately, a request with a seat and a purpose both set has no rule saying which check wins; a tool adapter (`am-tools` depends on `am-domain` and can name the enum) that sets both skips its seat's list if the purpose wins. "A test proves it" does not say what is proved or how.
- **Closing sentences (AD-12, App requests):** "A caller is exactly one of: a seat (with its Account when it has one), an Account alone, an MCP server, or an app purpose; this is one `am-domain` enum, a request with none of them is refused, and no request carries a purpose together with a seat, an Account or an MCP server. The `SkillImport` host set is consulted only for a request whose caller is that purpose; for every other caller the client behaves as if the set did not exist, and a test sends a seat, an Account, an MCP and a local-service-proxy request to each of the two hosts and requires each to be blocked. App requests are made through their own port (`am-domain`, adapter in `am-net`) that takes owner, repository and ref or SHA as typed values and builds the URL itself; `am-app` hands that port only to the skill-import command handler, and `cargo xtask check-deps` or a compile-fail test shows that `am-tools`, `am-connectors`, `am-mcp`, `am-providers`, `am-render` and the run loop cannot name it."
- The typed port also closes M1. If the architect prefers to keep one `send(HttpRequest)`, the first two sentences are the minimum.

### H4 — The imported skill's id is unruled, and so is a clash with an existing `skills/<id>/`

- **Spine text (AD-38):** "A skill in the archive is a folder at or below the URL's path that directly holds a `SKILL.md`"; "each chosen skill is its own import with its own Proposal". Nothing says what `<id>` the skill is written under, or what happens when `skills/<id>/` exists.
- **Loader fact:** `name` must equal the folder id and the id must be kebab-case (`kinds.rs` `fn skill`, `skills.rs` `load_all`).
- **Two builders.** One takes the id from the archive folder name (for a repository that is itself one skill, `SKILL.md` at the root, that is GitHub's `<owner>-<repo>-<sha7>` top folder, which is not the skill's name and changes with every commit). The other takes it from `name`. For `skills/Brainstorming/` with `name: brainstorming` they import under different ids, or one refuses and one rewrites `name` (a silent change to reviewed text). Story 4.11 creates files with `ConfigCreate` (create-without-replace); a 9.16 builder may make a replacing `ConfigEdit`.
- **Attack.** A hostile repository names its skill after one the project already attaches to seats (`house-style`). If the import replaces, the apply changes the instructions of every seat that attaches it with no attach step, and reference files of the old skill that the new one lacks either stay (a mix of two skills) or vanish. It is in a reviewed diff, but the "offers the seats to attach it to" step the owner expects never appears. Two skills in one archive with the same `name` under different parents (`a/x/`, `evil/x/`) make the CLI's `--skill x` ambiguous.
- **Closing sentences (AD-38, Several skills):** "The imported skill's id is its `name`, which must already be a kebab-case id; the archive's folder names are never used as the id, and the import never rewrites `name`. A skill whose `name` is not such an id, or is shared by two skills in the archive, or already exists as `skills/<id>/` in the project, is listed as 'cannot be imported' with the reason and gets no Proposal: v1 imports create and never replace (every file is a `ConfigCreate`); replacing is the v1.x update check. A skill is chosen by its path in the archive, shown beside its name."

## Medium

### M1 — `am-net` is told the two hosts, not the two request shapes, the headers or the redirect direction

- **Spine text (AD-12):** "`am-net` holds the purpose's host set as a compiled constant, exactly two hosts"; "a request with this purpose is a `GET` over https to port 443 with no body and no query string"; "each target is re-checked against the same two hosts and the same rules"; "Owner, repository, ref and path are checked against GitHub's name rules and percent-encoded per path segment before a request is built."
- **Holes.** (a) The paths are narrative; a host-only check lets a `SkillImport` request reach any `GET` on `api.github.com` (`/users/…`, `/gists/…`, `/repos/<o>/<r>/contents/…`), which is the "general fetch path" the Prevents line names. (b) Headers are free: only `Authorization` and cookies are named, so data can ride in any other header. (c) "GitHub's name rules" is not a rule two builders will write the same way, and percent-encoding does not stop dot segments: the URL type the client parses with (WHATWG rules) treats `..` and `%2e%2e` as "go up", so `/tree/x/../../../users/y` typed into the field makes the split loop of AD-38 ask `…/commits/x/..`, which normalises to another endpoint. The answer is thrown away (not 40 hex), but the request was made. (d) Redirect direction is free: a lookup may be redirected to `codeload.github.com` and codeload back to the API. (e) Who checks the names, the importer or the client? If only the importer does, the client is a general fetch path for whoever holds the port.
- **Closing sentences (AD-12, How), unless H3's typed port is taken, which gives (a), (b), (e) by construction:** "`am-net` itself refuses an app request whose first URL, after normalisation, is not `https://api.github.com/repos/<owner>/<repo>/commits/<ref>` or `…/zipball/<40 hex>`, and sends exactly two headers, the user agent and `Accept`. A lookup's redirect must stay on `api.github.com`; only the archive request may be redirected to `codeload.github.com`, which is never contacted first. Owner and repository match `[A-Za-z0-9._-]{1,100}` and are not `.` or `..`; every ref and path segment is non-empty, is not `.` or `..`, and holds no `%`, `\`, `?`, `#`, space or control character; the typed URL is percent-decoded once before these checks."

### M2 — Who writes the audit entry for an app request, as which actor, and when

- **Spine text (AD-12):** "every request with an app purpose, allowed or blocked, is an audit entry by that Human actor through the open project's writer"; and, earlier in the same AD, "A blocked call is written to the audit log and shown in Doctor."
- **Built code:** `NetEgress::audit_block` writes `egress.blocked` through `AuditSink` with `Actor::System { component: "am-net" }`; the request carries no Actor.
- **Two builders.** The client's builder keeps auditing blocks itself (System actor); the import's builder writes one entry per request with the Human actor. A blocked redirect then has two entries with two actors, or, if each thinks the other does it, none for allowed requests. The spine also does not say whether an allowed request is recorded before it is sent or after (the entry holds "outcome" and the archive sha256, so after), so a crash mid-download leaves a request with no record.
- **Closing sentence:** "The skill-import command handler, not `am-net`, writes these entries: the client returns each request's host, path and outcome (redirect hops included) to the caller and its own blocked-egress sink writes nothing for an app purpose; the handler commits one entry per request before the next request is sent, and an entry that cannot be written stops the import. The path is stored as sent, cut to 512 characters; a redirect's `Location` is untrusted text and is stored only after it passed the client's checks."

### M3 — The CLI start: which process, which writer, and a child that can hold the CLI token

- **Spine text (AD-15):** "on an interactive TTY and only while no stdio MCP server is enabled in the project … starting a skill import from a GitHub URL"; **(AD-12):** "through the open project's writer". Architect assumption (a) in the memlog: "so a same-user child holding the CLI token cannot make the app fetch".
- **Holes.** (a) The interim Account edit says "no CLI-token API route" and "runs in its own process"; this amendment says neither. If the import is a CLI-token route on the running server, the TTY check lives in the CLI binary and the server cannot see it: any process that can read the 0600 token file starts imports. (b) AD-13 keeps the token from the extract child only while the App Sandbox holds. With "Run parsers without OS isolation" on (and on every non-macOS dev build, story 4.16), the child that expands the downloaded archive runs as the owner, can read the token, and can start further imports of attacker-chosen repositories: a loop of fetches and Proposals with no human, fed by hostile bytes from the network. The CLI-class refusal names stdio MCP and render Sources only.
- **Closing sentences (AD-15, CLI class):** "The CLI start of a skill import is a CLI-token route on the running server (the open project's writer records it); the server refuses it while a stdio MCP server or a Source with `render: true` is enabled, and also while 'Run parsers without OS isolation' is on or the sandbox self-test has not passed, naming the UI. One import runs at a time per project; a second start is refused in words." (If the architect prefers a separate process as for `accounts add`, say so and say it holds the store lock; the unsandboxed-parser clause is needed either way.)

### M4 — The ref and path split: which answers mean "try a longer ref", and the budget of 8 does not add up

- **Spine text (AD-38):** "where `<ref>` ends and `<path>` begins is settled by lookups, shortest ref first"; **(AD-12):** "One import command makes at most 8 requests, redirects included, at least 1 s apart per host".
- **Holes.** (a) The spine does not say which answers continue the loop. 422 means "no such ref" (memlog); 404 means the repository is missing or private; 403 or 429 is the rate limit; a 200 that is not 40 hex is a wrong endpoint. A builder who continues on any non-200 burns the budget against a private repository and reports "no such branch". (b) Budget: the archive costs 2 (request and redirect). That leaves 6 lookups. A renamed repository answers 301 on every lookup (memlog), halving it to 3 candidates; H1's `heads/` then `tags/` halves it again. `…/tree/release/2026/q4/skills/x` on a renamed repository fails though every rule was followed. (c) A tag `release` and a branch `release/v2` can coexist; shortest-first picks the tag while GitHub's own page for the same URL may show the branch, so the owner reviews one tree on the web and imports another. The diff still shows what will be written; the confirm step should say which split was taken.
- **Closing sentences (AD-38, Pin):** "Only a 422 answer moves to the next longer candidate; any other answer ends the import in words (404: not found or private; 403 or 429: rate limit with the reset time). At most 4 candidates are tried. After a 301 the import uses the redirected repository address for its remaining requests. The confirm step shows the ref and the path as resolved, separately." **(AD-12):** raise the cap to fit: "at most 12 requests".

### M5 — "Listed" and "named" have no size, and untrusted names reach a terminal

- **Spine text (AD-38):** "they are listed by `name` and `description`, shown as plain text cut to 64 and 1,024 characters"; "Everything the format above does not accept is **left out and named**"; "the import summary names them".
- **Scenarios.** (a) A repository with 50,000 one-line `SKILL.md` folders fits in 64 MB; the list is 50,000 rows of up to 1,088 characters. (b) "Named" covers every file outside the skill folders: the acceptance example alone leaves about 290 entries out, a monorepo leaves 100,000, and with one Proposal per chosen skill each Proposal may repeat the whole list in its summary, its History entry and its Inbox card. (c) `agentic skills import` prints the list, the left-out names and the diff to an interactive terminal. Names, descriptions, file names, diff lines and GitHub's error text are untrusted and can carry terminal escape sequences (clipboard write, title change, cursor moves that redraw the list) and bidirectional overrides that make two rows look alike in the UI and the CLI. No rule in the spine cleans CLI output.
- **Closing sentences (AD-38):** "At most 200 skills are listed; past that the import is refused in words asking for a narrower folder URL. Repository-level leftovers are shown once, in the list step, grouped by top-level entry with a count, at most 100 lines and then 'and N more'; each Proposal names only what was left out of its own skill folder, with the same limit. Every string that comes from the archive or from a host's answer is shown, in the UI and in the CLI, with control characters (C0, C1, DEL) and bidirectional and zero-width formatting characters replaced by a visible escape."
- The last sentence belongs in Consistency Conventions as a general CLI and untrusted-well rule; the zip and department imports (4.11) need it too.

### M6 — Names that are one file on APFS and two in the archive; duplicate zip entries; reference file names

- **Spine text (AD-38, Same path):** "from there on it is a zip import: the same caps, `WorkspacePath` checks…". AD-30 compares config names "ignoring case and Unicode normalisation (APFS's default)", but only for config names.
- **Scenario.** One skill folder holds `SKILL.md` and `skill.md`, or `references/a.md` and `references/A.md`, or two zip entries with the same path. The list and diff are drawn from the entry stream; the temporary folder (APFS, case-insensitive) or the project folder keeps one of them, not necessarily the one shown. With H2 fixed the applied bytes are the Proposal's, but which of the two the Proposal holds is still builder's choice, and the apply's second `ConfigCreate` fails half-way. Reference file names also enter prompts by name (AD-27) and may be 65,535 bytes long.
- **Closing sentence (AD-38):** "A skill folder in which two entries have the same path, or paths equal ignoring case and Unicode normalisation, cannot be imported and says why; an accepted file name matches `[A-Za-z0-9._-]{1,100}`, and any other name is left out and named."

### M7 — A SKILL.md the loader refuses: left out, repaired or refused?

- **Spine text (AD-38):** "Everything the format above does not accept is **left out and named** … never a reason to refuse the skill: `scripts/`, executables, links, other extensions, and any file or folder outside `SKILL.md` and `references/`"; "The import writes two fixed keys into the imported SKILL.md's existing `metadata` map"; "The skill format, the loader and `agentic validate` are unchanged".
- **Loader facts:** an unknown frontmatter key is an error (`fields.rs` `allow`; `SKILL_KEYS` has five keys, and the open format also defines `compatibility`); a nested `metadata` value is an error; a body over 64 KB, a reference over 256 KB and more than 20 references are errors; text that looks like a key (`sk-…`, `ghp_…` in an example) is an error.
- **Holes.** "Left out and named" lists files only. For frontmatter keys and size limits, one builder strips and names, one refuses, one imports and leaves the project failing `agentic validate` after apply (story 9.16's verify requires it to pass). "Existing `metadata` map" has no rule for a SKILL.md with no `metadata`, or with `metadata` that is a list or a string. Who emits the final text is open too: AD-16 says only `am-config` writes project files and that its writer drops YAML comments and reorders keys, so the text reviewed must be the text that writer produces.
- **Closing sentences (AD-38, Source record):** "`am-config` builds the SKILL.md text the import will write, by one function the diff and the apply both use: the frontmatter re-emitted in canonical order with the two keys added (a `metadata` map is created when the file has none), the body byte for byte. A skill whose result would not pass `agentic validate` is listed as 'cannot be imported' with the validator's own words and gets no Proposal; the import leaves out files, never keys or text. An oversize or surplus reference file is a left-out file." (Whether unknown frontmatter keys such as `compatibility` should instead be left out and named is an owner or architect choice; say one or the other.)

### M8 — One Proposal per skill against AD-15's batch confirmation

- **Spine text (AD-38):** "each chosen skill is its own import with its own Proposal"; **(AD-15, Batch):** "one confirm token may cover several pending widenings listed together in one review dialog".
- **Clash.** The memlog reads the first as "two ticked skills are two two-step confirmations" (assumption b). The 5.11 dialog builder, following AD-15, shows "Review 15 changes…" under one token. A hostile repository wants exactly that: fifteen ticked skills, one of them poisoned, one confirmation.
- **Closing sentence (AD-38, Several skills):** "AD-15's batch confirmation does not cover import Proposals: each imported skill is confirmed with its own token after its own full diff." (Or state the opposite; it must be stated.)

### M9 — Ticket clash for Sofia: story 2.2's no-telemetry test, and which story lands the enum and the constant

- **Spine text (AD-12):** "their expected list of fixed hosts in the binary holds `api.github.com` and `codeload.github.com` under `SkillImport`, and they fail … on any other fixed host the tests do not name."
- **Ticket text (epic 2 story 2, verify):** "CI fails if any host outside configured Accounts, seat allow-lists and the release host appears in the binary's egress configuration".

## Low

- **L1 — Caps on the whole archive or on the chosen subtree.** "expanded only in the `agentic __extract` child under the AD-30 archive caps" does not say whether the caps count the whole repository or only the entries at or below the URL's path, nor whether the path filter runs in the child. A large honest repository with a small `skills/` folder is refused by one builder and accepted by the other, and the extract protocol differs. Sentence: "The child is given the path prefix and expands only `SKILL.md` and `references/` entries at or below it; every other entry is listed by name without being expanded; the archive caps count what is expanded, and the entry count has its own cap." The AD-30 archive caps have no numbers in the spine; they should have (ticket 4.6 owns them).
- **L2 — Forged source keys on the other import paths, and the deferred update check.** "a folder, zip or department import keeps such keys as the file's own text" lets a zip carry `agentic-source-url: https://github.com/<trusted>/…`; any later screen that shows "Source" for a skill, and the v1.x check that "needs no migration" because the file records its source, would then trust a forged claim. Sentence (AD-38): "No screen shows these keys as the app's own statement; the app's record of an import is its History and audit entry." Deferred row: "the check shows the recorded URL as the file's claim and asks before fetching".
- **L3 — Renamed or transferred repositories.** The lookup's 301 goes to `/repositories/<id>/…`; the confirm step and the record show the typed name while the bytes came from wherever the name now points, and a freed name can be re-registered by someone else. Sentence: "When a lookup was redirected, the confirm step says the repository has moved." Recording the numeric repository id for the v1.x check is a Deferred note.
- **L4 — Spacing and limits across commands.** "at least 1 s apart per host" and "at most 8 requests" are per command; nothing limits commands. With M3's one-import-at-a-time rule this is closed; otherwise add "spacing is per host across all app requests".
- **L5 — AGENTS.md Policy was not refreshed.** It says "every website fetch through `Fetcher`" and "No … named source sites and hosts in `crates/`"; a builder or reviewer reading it to the letter flags the archive download and the two host constants in `am-net`, and the UI's "GitHub" label in `web/src`. `xtask/denylist.txt` has no such entry today, so CI passes. Not a spine change: one line through `bmad-project-context` saying the `SkillImport` set in `am-net` is the one named-host exception and that app requests are API calls outside `Fetcher`.
- **L6 — Typed URL forms (ticket 9.16).** The spine's "any other host or URL form is refused in words" is enough; the ticket should list the refusals a builder will otherwise guess: `http://`, `www.github.com`, an upper-case host, a trailing slash, `.git`, `/blob/…/SKILL.md` (the link an owner is most likely to copy; the refusal should say "give the folder's link"), a query or fragment, and a userinfo part.

## Attacks tried that the rules as written do stop

- A ref that moves between lookup and download: the archive is asked for by SHA, never by ref.
- A redirect to a third host, a private address or a rebinding answer: re-checked on every hop, same resolver and pinning.
- A seat, tool, tainted step or the Assistant reaching the two hosts through the set: the set is outside config and outside `allowed_hosts`; ToolGate and the tainted-read rule are unchanged (subject to H3's wording so the client agrees).
- Credential leak to GitHub: no `Authorization`, no cookie, no keychain read.
- Zip bomb, symlink entries, `../` names: AD-30 caps and `WorkspacePath`, in the sandboxed child, with links left out by AD-38.
- `allowed-tools`, `scripts/`, hooks and plugin manifests gaining effect: AD-38's "a skill grants nothing" and "left out and named" hold.
- Forged `agentic-source-*` keys in a GitHub import: replaced by what the app resolved (but see H1 for what "resolved" proves, and L2 for the other paths).
- Injected text in `name` or `description` reaching a prompt before apply: "never placed in a prompt"; content stays `UntrustedData` until the owner's apply, and a tainted reader's Proposal is never approvable (AD-10 (b)).
- Data leaving through the fixed hosts: `GET` only, no body, no query; the only free text is the path the owner typed (M1 tightens headers and path shape). The residual channel is the request path to GitHub itself, which a repository owner cannot read.
